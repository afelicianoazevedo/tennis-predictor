# Tennis Predictor — Especificação inicial do projeto

## 1. Objetivo

Desenvolver uma aplicação web progressiva (PWA) para utilização pessoal, orientada para análise e previsão de jogos de ténis.

A aplicação deverá utilizar:

* Frontend: HTML5 + CSS3 + JavaScript
* PWA instalável em Android e desktop
* Backend/serverless: Supabase Edge Functions
* Base de dados: Supabase PostgreSQL
* Fonte de dados: Live Tennis API
* Desenvolvimento no VS Code
* Código preparado para funcionar em ambiente local e posteriormente em produção

Não utilizar frameworks pesados no frontend nesta primeira fase. Manter a aplicação simples, modular e fácil de manter.

---

# 2. Objetivos funcionais

A aplicação deverá permitir:

1. Consultar jogos dos próximos 3 dias.
2. Identificar os jogos do dia.
3. Consultar resultados de jogos terminados.
4. Apresentar informação dos jogadores.
5. Apresentar estatísticas relevantes para previsão, quando disponíveis.
6. Apresentar H2H quando os dados estiverem disponíveis.
7. Apresentar odds quando a API/plano utilizado as disponibilizar.
8. Calcular/apresentar probabilidades de vitória.
9. Atribuir uma classificação de confiança a cada jogo.
10. Guardar as previsões realizadas.
11. Depois do resultado final, comparar previsão com resultado real.
12. Permitir posteriormente avaliar a eficácia do sistema de previsão.
13. Ter uma área de jogos LIVE, mas esta NÃO é a prioridade da aplicação.

---

# 3. Sistema de classificação

A aplicação terá quatro níveis de confiança.

|  Score | Classificação | Cor          |
| -----: | ------------- | ------------ |
|   0–49 | Incerto       | Vermelho     |
|  50–59 | Perigoso      | Amarelo      |
|  60–69 | Tendência     | Verde claro  |
| 70–100 | Forte         | Verde escuro |

É muito importante que o verde claro e o verde escuro sejam visualmente distintos.

Usar, por exemplo:

* Verde claro: #90EE90
* Verde escuro: #006400

Além da cor, apresentar sempre o nome textual da classificação e o score.

Exemplo:

"FORTE — 78/100"

Nunca utilizar apenas a cor para transmitir informação.

---

# 4. Filosofia de utilização da API

A aplicação utiliza a versão FREE da Live Tennis API.

Limite conhecido:

* 100 requests por dia
* 30 requests por minuto

O sistema deve assumir um limite operacional de 90 requests/dia, mantendo 10 requests como margem de segurança.

Nunca ultrapassar os 100 requests/dia.

O sistema NÃO deve distribuir obrigatoriamente 100 requests de forma uniforme ao longo do dia.

Deve utilizar os requests de forma dinâmica, de acordo com a prioridade.

---

# 5. Prioridade dos requests

A prioridade é:

1. Jogos dos próximos 3 dias
2. Jogos que começam nas próximas horas
3. Dados necessários para construir previsões
4. Odds/probabilidades, quando disponíveis
5. Resultados de jogos que já terminaram
6. Atualização de estatísticas
7. Informação secundária
8. Live scores

O LIVE não deve consumir a maior parte da quota.

Não fazer polling contínuo dos jogos LIVE.

Se não houver necessidade, não fazer requests.

Antes de cada chamada à API:

1. verificar a utilização diária;
2. verificar se o limite operacional de 90 foi atingido;
3. verificar se os dados já existem em cache/base de dados;
4. verificar quando foram atualizados pela última vez;
5. determinar a prioridade;
6. só então executar a chamada.

---

# 6. Estratégia temporal

Se os primeiros jogos do dia começarem, por exemplo, às 15:00:

Durante a manhã:

* pesquisar/atualizar a lista de jogos;
* preparar os jogos dos próximos 3 dias;
* obter os dados necessários dos jogadores;
* preparar os dados necessários para previsão.

Antes das 15:00:

* concentrar os requests nos jogos que começam nas próximas horas;
* atualizar dados relevantes;
* atualizar odds, quando disponíveis;
* calcular/recalcular previsões.

Depois das 15:00:

* não fazer polling agressivo;
* consultar resultados em blocos;
* atualizar jogos terminados;
* guardar os resultados;
* comparar resultados com as previsões.

No final do dia:

* fechar resultados;
* guardar desempenho das previsões;
* preparar os dados para o dia seguinte.

A aplicação deve ser concebida para que a PWA não precise de estar aberta para que estes processos aconteçam.

# 9. Gestão dos requests

Já existem funções PostgreSQL:

* get_api_usage()
* register_api_request()
* can_make_api_request()

A função can_make_api_request() utiliza 90 requests como limite operacional.

A lógica de consumo da API deve ser centralizada.

Não permitir que vários componentes façam chamadas independentes sem controlo da quota.

Criar uma camada única responsável pelas chamadas à Live Tennis API.

Cada request deve ser registado em api_requests.

Registar:

* endpoint
* parâmetros
* hora
* status HTTP
* sucesso/erro
* tempo de resposta
* tipo de request
* mensagem de erro

---

# 10. Cache

Antes de fazer qualquer chamada à API, verificar se os dados já estão disponíveis no Supabase e se continuam válidos.

A aplicação deve privilegiar:

PWA → Supabase

em vez de:

PWA → Live Tennis API

A Live Tennis API deve ser usada apenas para atualizar os dados.
